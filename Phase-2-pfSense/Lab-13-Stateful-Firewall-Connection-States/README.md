## What Is a Stateful Firewall?

A stateful firewall does more than evaluate isolated packets.

When pfSense permits network communication, it can create a **state** representing the connection.

For a TCP connection, a state can contain information such as:

```text
Protocol
Source IP
Source Port
Destination IP
Destination Port
Connection state
NAT translation
```

This allows the firewall to recognize packets that belong to an existing connection.

Instead of treating every returning packet as completely unrelated traffic, pfSense can associate it with a connection already being tracked.

## Identifying the Connection State

Immediately after generating the connection, the pfSense state table was inspected.

The LAN-side state showed:

```text
Source:
192.168.50.101:57863

Destination:
104.20.23.154:80
```

This can be interpreted as:

```text
Windows 11
192.168.50.101:57863
        ↓
      TCP
        ↓
104.20.23.154:80
External Web Service
```

Port `57863` was the temporary client-side source port.

Port `80` represented the destination HTTP service.

## Ephemeral Source Ports

The connection used:

```text
192.168.50.101:57863
```

The port:

```text
57863
```

was an **ephemeral source port** selected for the client connection.

This differs from the destination service port:

```text
80
```

The destination server listens for HTTP traffic on TCP/80, while the client uses a temporary high-numbered port to identify its side of the connection.

Conceptually:

```text
Client                         Server

192.168.50.101:57863  ──────►  104.20.23.154:80
                  TCP connection
```

## Observing NAT in the State Table

The WAN-side state displayed:

```text
10.0.2.15:35226 (192.168.50.101:57863)
→
104.20.23.154:80
```

This provided a direct view of NAT translation occurring through pfSense.

The original LAN-side connection was:

```text
192.168.50.101:57863
```

On the WAN side, pfSense represented the connection as:

```text
10.0.2.15:35226
```

Conceptually:

```text
192.168.50.101:57863
        │
        │ LAN
        ▼
     pfSense
        │
        │ NAT
        ▼
10.0.2.15:35226
        │
        │ WAN
        ▼
104.20.23.154:80
```

pfSense maintained the relationship between the original internal connection and the translated WAN-side connection.

## Why NAT State Tracking Matters

The external destination does not communicate directly with:

```text
192.168.50.101
```

That address exists on the internal SEC-LAB network.

Instead, outbound traffic is translated through pfSense.

In this lab:

```text
Internal:
192.168.50.101:57863

Translated:
10.0.2.15:35226
```

pfSense tracks this relationship so that returning traffic associated with the translated connection can be mapped back to the appropriate internal connection.

This demonstrated how **state tracking and NAT work together**.

## Creating a New Firewall Block Rule

A temporary firewall rule was created to block new HTTP connections from Windows 11.

The rule was configured as:

| Setting | Value |
|---|---|
| Action | Block |
| Protocol | TCP |
| Source | `192.168.50.101` |
| Destination | Any |
| Destination Port | HTTP / TCP 80 |
| Logging | Enabled |
| Description | `LAB13 - Block Win11 HTTP` |

The rule was positioned above the broad default allow policy.

Conceptually:

```text
IF
    Source = 192.168.50.101
AND Protocol = TCP
AND Destination Port = 80
THEN
    BLOCK
```

## Rules vs States

This lab demonstrated an important distinction between a **firewall rule** and a **firewall state**.

### Firewall Rule

A firewall rule defines policy.

Example:

```text
BLOCK
192.168.50.101
→
TCP/80
```

The rule answers:

```text
Should matching traffic be allowed or blocked?
```

### Firewall State

A state represents a connection being tracked by the firewall.

Example:

```text
192.168.50.101:57863
→
104.20.23.154:80
```

The state answers:

```text
What connection is pfSense currently tracking?
```

Rules define policy.

States represent tracked network communication.

---

## Short-Lived TCP States

The connection generated using:

```powershell
Test-NetConnection
```

was short-lived.

When the state table was inspected later, the previous connection state was no longer present.

This demonstrated an important troubleshooting lesson:

> A state table is dynamic.

States are created and removed as connections begin, terminate, or expire.

Seeing a connection at one moment does not mean that the same state will remain indefinitely.

---

## Existing States vs New Connections

The lab originally attempted to investigate how an already-established connection behaves after a firewall rule change.

However, the initial TCP connection generated by `Test-NetConnection` terminated too quickly to provide a reliable persistent-state test.

Therefore, this lab does **not** claim to have demonstrated that an established TCP connection remained active after a firewall policy change.

What was directly demonstrated was:

```text
1. TCP connection established successfully
2. pfSense created observable state information
3. LAN and WAN state information was inspected
4. NAT translation was observed
5. The short-lived state later disappeared
6. A new block policy was applied
7. A new TCP connection was attempted
8. The new connection was blocked
9. Firewall logs confirmed the enforcement
```

This distinction is important because security documentation should describe what was actually observed rather than what was expected theoretically.

## Connection Identification

A TCP flow can be distinguished using information including:

```text
Source IP
Source Port
Destination IP
Destination Port
Protocol
```

For example:

```text
TCP

192.168.50.101:57863
        ↓
104.20.23.154:80
```

A later TCP connection between the same two IP addresses can use a different client-side ephemeral port and therefore represent a different flow.

This is why a firewall state should not simply be interpreted as:

```text
Windows 11 is allowed to communicate with this server forever.
```

The state corresponds to particular tracked network communication.

---

## Stateful vs Stateless Thinking

A simplified stateless approach evaluates packets primarily according to configured packet-filtering criteria.

Stateful inspection adds awareness of connection state.

Conceptually:

```text
Packet arrives
      ↓
Does it belong to a tracked state?
      ↓
Stateful firewall processes traffic
with connection context
```

This capability is particularly important for return traffic.

When an internal client initiates an allowed connection, pfSense can track the communication and recognize traffic associated with that connection.

## Conclusion

Lab 13 demonstrated that pfSense does more than evaluate individual firewall rules.

As a stateful firewall, pfSense maintains information about network connections and uses a state table to track communication passing through the firewall.

Inspection of the LAN and WAN states showed how an internal connection:

```text
192.168.50.101:57863
```

was associated with the translated WAN-side connection:

```text
10.0.2.15:35226
```

while communicating with:

```text
104.20.23.154:80
```

The lab also demonstrated the distinction between **policy and state**:

```text
Firewall Rules = What traffic should be permitted or denied

Firewall States = Connections currently being tracked
```

Understanding this distinction is essential for firewall administration, network troubleshooting, NAT analysis, and security investigations.
