# Lab 01 — ARP & ICMP Packet Analysis

## Objective

The objective of this lab was to capture and analyze ARP and ICMP network traffic using Wireshark.

This lab demonstrates how a Windows workstation resolves the MAC address of another device on the local network before sending ICMP traffic.

---

## Lab Environment

| System | Role | IP Address |
|---|---|---|
| Win11Pro | Source Workstation | 192.168.50.101 |
| pfSense | Router / Default Gateway | 192.168.50.1 |
| DC-01 | Active Directory / DNS | 192.168.50.10 |

**Internal Network:** `SEC-LAB`

**Subnet:** `192.168.50.0/24`

---

## Tools Used

- Wireshark
- Windows PowerShell
- pfSense
- Oracle VirtualBox

---

## Traffic Generation

Wireshark was started on the Windows 11 Ethernet interface connected to the `SEC-LAB` network.

The existing ARP entry for the default gateway was removed to force Windows to perform a new ARP resolution.

```powershell
arp -d 192.168.50.1
```

ICMP traffic was then generated by pinging the pfSense default gateway.

```powershell
ping 192.168.50.1
```

The following Wireshark display filter was used to isolate ARP and ICMP traffic:

```text
arp || icmp
```

# ARP Analysis

## ARP Request

Before Win11Pro could send ICMP traffic to pfSense, the workstation needed to determine the MAC address associated with `192.168.50.1`.

Win11Pro transmitted an ARP request:

```text
Who has 192.168.50.1? Tell 192.168.50.101
```

The ARP request contained:

- Sender IP: `192.168.50.101`
- Sender MAC: Win11Pro MAC address
- Target IP: `192.168.50.1`
- Target MAC: Unknown
- Opcode: ARP Request

This demonstrates how ARP resolves a local IPv4 address to a Layer 2 MAC address.

## ARP Reply

pfSense responded to the ARP request and provided the MAC address associated with `192.168.50.1`.

The response effectively informed Win11Pro:

```text
192.168.50.1 is at [pfSense MAC Address]
```

Win11Pro could then associate the Layer 3 IPv4 address of the gateway with its Layer 2 MAC address.

The mapping could also be stored temporarily in the workstation's ARP cache, preventing ARP resolution from being required before every packet.

# ICMP Analysis

## ICMP Echo Request

After resolving the pfSense MAC address, Win11Pro was able to construct the Ethernet frame and send the ICMP packet.

The workstation transmitted an ICMP Echo Request:

```text
192.168.50.101 → 192.168.50.1
```

The captured packet contained:

- ICMP Type: `8`
- ICMP Code: `0`
- Source IP: `192.168.50.101`
- Destination IP: `192.168.50.1`

ICMP Type 8 represents an Echo Request.

## ICMP Echo Reply

pfSense received the Echo Request and responded with an ICMP Echo Reply.

The captured reply traveled in the opposite direction:

```text
192.168.50.1 → 192.168.50.101
```

The packet contained:

- ICMP Type: `0`
- ICMP Code: `0`
- Source IP: `192.168.50.1`
- Destination IP: `192.168.50.101`

ICMP Type 0 represents an Echo Reply.

This confirmed successful Layer 3 communication between Win11Pro and the pfSense gateway.

# Packet Flow

The captured traffic demonstrated the following communication sequence:

```text
Win11Pro (.101)                         pfSense (.1)
      |                                      |
      | ---- ARP Request ------------------> |
      |                                      |
      | <--- ARP Reply --------------------- |
      |                                      |
      | ---- ICMP Echo Request ------------> |
      |                                      |
      | <--- ICMP Echo Reply --------------- |
      |                                      |
```

The sequence can be summarized as:

```text
Destination IP known
        |
        v
Destination MAC unknown
        |
        v
ARP Request
        |
        v
ARP Reply
        |
        v
MAC address learned
        |
        v
ICMP Echo Request
        |
        v
ICMP Echo Reply
        |
        v
Connectivity Confirmed
```

# ARP Cache Behavior

ARP resolution does not normally occur before every packet.

After Win11Pro learned the MAC address associated with `192.168.50.1`, Windows could temporarily store the mapping in its ARP cache.

Conceptually:

```text
192.168.50.1 → pfSense MAC Address
```

Subsequent traffic could use the cached MAC address until the entry expired or was removed.

During this lab, the ARP entry was manually deleted to force Windows to generate a new ARP request.

---

# Local vs Remote Communication

ARP operates on the local Layer 2 network.

For example, Win11Pro was configured as:

```text
IP Address:      192.168.50.101
Subnet:          192.168.50.0/24
Default Gateway: 192.168.50.1
```

When communicating directly with `192.168.50.1`, Win11Pro could use ARP to determine the gateway's MAC address because both interfaces were on the local subnet.

If Win11Pro instead needed to communicate with a remote address such as:

```text
8.8.8.8
```

Windows would recognize that `8.8.8.8` is outside `192.168.50.0/24`.

The workstation would not ARP for the MAC address of `8.8.8.8`.

Instead, the traffic would be sent toward the default gateway:

```text
192.168.50.1
```

If the gateway's MAC address was unknown, Win11Pro would use ARP to resolve the MAC address of the gateway.

The IP packet could therefore have:

```text
Destination IP: 8.8.8.8
```

while the local Ethernet frame would be addressed to the MAC address of pfSense.

---

# Security Relevance

ARP does not provide built-in authentication of ARP responses.

A malicious system with access to the local network may attempt to send falsified ARP information and associate its own MAC address with the IPv4 address of another system.

This technique is commonly known as:

**ARP Spoofing / ARP Poisoning**

Successful ARP poisoning can potentially assist an attacker with man-in-the-middle activity by manipulating how local systems forward Ethernet traffic.

From a defensive perspective, packet analysis tools such as Wireshark can help investigate:

- Unexpected ARP responses
- Abnormal IP-to-MAC mappings
- Repeated or unusual ARP activity
- Changes in MAC addresses associated with important systems
- Suspicious communication between local hosts

Understanding normal ARP behavior provides a baseline for recognizing abnormal Layer 2 activity.

# Key Findings

During this lab, I observed that:

1. Knowing a destination IPv4 address is not always sufficient for local Ethernet communication.
2. A workstation needs the destination's Layer 2 MAC address to construct the Ethernet frame.
3. ARP can resolve a local IPv4 address to a MAC address.
4. The ARP request asked which system owned `192.168.50.1`.
5. pfSense responded with its MAC address.
6. Windows could then cache the IP-to-MAC mapping.
7. ICMP Type 8 was used for the Echo Request.
8. ICMP Type 0 was used for the Echo Reply.
9. Source and destination IP addresses reversed between the ICMP request and reply.
10. Remote destinations are reached through the default gateway rather than by ARPing directly for the remote host.
